# Contributing to OSEF

Thank you for your interest in contributing to the Operating Systems Engineering Framework (OSEF).

OSEF is an engineering specification for Intelligent Operating Systems. Every contribution should improve the framework while preserving its consistency, traceability, and long-term maintainability.

---

# Before You Start

Before contributing, please read the following documents:

- Manifesto
- Core Principles
- Vision
- OSEF Specification
- Governance
- Architecture
- Versioning Specification
- Document ID Specification

Understanding these documents is essential before proposing changes.

---

# Guiding Principles

Every contribution should follow these principles:

- Engineering before automation.
- Architecture before implementation.
- Specification before code.
- Reuse before creation.
- Simplicity over unnecessary complexity.
- Human oversight for critical decisions.
- Continuous improvement.

---

# Types of Contributions

OSEF welcomes contributions in several areas.

## Engineering Specification

Examples include:

- new specifications;
- improvements to existing specifications;
- clarifications;
- editorial corrections.

---

## Governance

Examples include:

- RFC process improvements;
- versioning rules;
- document standards;
- traceability improvements.

---

## Runtime

Examples include:

- schemas;
- templates;
- validators;
- generators;
- CLI improvements.

---

## Reference Implementations

Examples include:

- Personal OS
- Marketing OS
- future domain implementations

Reference implementations help validate the framework through real-world usage.

---

## Documentation

Documentation is considered part of the product.

Examples:

- tutorials;
- examples;
- diagrams;
- migration guides;
- educational material.

---

# Contribution Workflow

Every contribution should follow this process.

```
Issue
    ↓
Discussion
    ↓
Proposal
    ↓
Review
    ↓
Approval
    ↓
Implementation
    ↓
Validation
    ↓
Merge
```

Significant engineering changes should begin with an RFC.

---

# Pull Requests

Every Pull Request should:

- address a clearly defined problem;
- remain focused on a single topic;
- include appropriate documentation updates;
- preserve backward compatibility whenever practical;
- follow the project conventions.

---

# Commit Guidelines

Use clear and descriptive commit messages.

Examples:

```
docs: improve Architecture specification

spec: add Versioning rules

runtime: add schema validator

governance: update RFC process
```

---

# Coding Standards

Implementation should:

- follow the official specifications;
- remain modular;
- avoid unnecessary dependencies;
- include validation where appropriate;
- preserve traceability.

---

# Documentation Standards

Documentation should:

- use clear English;
- remain consistent with the Glossary;
- follow the Versioning Specification;
- include document metadata where required.

Documentation should evolve together with the implementation.

---

# Reporting Issues

Bug reports should include:

- description;
- expected behavior;
- observed behavior;
- reproduction steps;
- affected version.

Feature requests should explain:

- the problem;
- the proposed solution;
- expected benefits;
- possible alternatives.

---

# Review Process

Contributions are reviewed according to:

- engineering quality;
- architectural consistency;
- specification compliance;
- documentation quality;
- long-term maintainability.

Approval is based on technical merit rather than implementation size.

---

# Community

OSEF aims to build a collaborative engineering community.

Contributors are encouraged to:

- ask questions;
- discuss ideas;
- challenge assumptions respectfully;
- share knowledge;
- help improve the framework.

Engineering grows through collaboration.
